# scent-studio 서버 설계안 (plan.md 단계 4) — 사장 검토용

> 2026-11-06 백엔드팀 작성, 1판. **사장 승인 전에는 서버 코드를 만들지 않는다.** 바탕: design.md 11·12-1·16절, `db_design.md` 3판(표 6개, 실제 DB 적용 완료), 보안 규칙 `.claude/rules/security.md`.
> "(확인 필요)"는 서비스 정책·요금이 바뀔 수 있어 고를 때 공식 문서로 다시 확인할 것.

## 1. 큰 그림
- **Java 21 + Spring Boot 4.1**, `backend/`에 그대로 더한다(지금 있는 Flyway 마이그레이션·DB 테스트 위에).
- 서버가 하는 일은 셋뿐: ① 로그인한 사용자 데이터(취향·조합·찜·시향 기록·동의) ② 카탈로그 새 버전 알려 주기 ③ 사용 기록 받기. **추천 계산은 하지 않는다**(앱 안에서, D1).
- DB는 `scent_server` 계정으로만(실제 DB에서 권한 확인 끝남). 서비스 비밀 키(Supabase Secret key)는 **계정 삭제에만** 쓰고 서버 환경 변수에만 둔다.
- 모든 응답 JSON, 주소 앞에 `/api/v1`. 오류는 `{"error": {"code": "...", "message": "..."}}`.

## 2. API 목록
"로그인"은 Supabase 로그인 토큰(`Authorization: Bearer <토큰>`)이 필요하다는 뜻. 사용자 id는 **토큰에서만** 꺼내고 주소·본문의 사용자 id는 받지 않는다.

| 주소 | 하는 일 | 로그인 | 승인 항목 |
|---|---|---|---|
| `GET /health` | 서버와 DB가 살아 있나(`select 1`). 일시 정지 방지 예약 작업이 이걸 부르게 바꾼다 | — | — |
| `GET /catalog/latest` | 최신 카탈로그 `{version, sha256, size, url, minAppVersion}` | — | E2(오프라인 대비) |
| `GET /me` | 내 계정(이메일, 가입일), 지금 동의해야 할 문서 버전과 내 동의 상태 | 필요 | S11 |
| `DELETE /me` | **계정 삭제**: Supabase에 계정 삭제 요청 → DB가 내 데이터 한 번에 정리(`db_design.md` 4절) → "남은 줄 0개" 확인 후 응답 | 필요 | G1·G2 |
| `POST /me/consents` | 약관·방침·만 14세 확인 동의 기록(버전마다 쌓임) | 필요 | — |
| `GET /me/preferences` · `PUT /me/preferences` | 불호 노트·선호 계열 읽기·바꾸기 | 필요 | C1~C3 |
| `POST /me/preferences/merge` | 로그인 직후 기기 값과 합치기(불호 합집합, 선호는 서버 우선, 200개 상한) → 합친 값 돌려줌 | 필요 | D6 |
| `GET /blends` · `POST /blends` | 내 조합 목록 · 저장(한도 100) | 필요 | D2·D5 |
| `GET /blends/{id}` · `PUT /blends/{id}` · `DELETE /blends/{id}` | 조합 하나 읽기·이름 등 바꾸기·지우기 (내 것만, 남의 id면 404) | 필요 | D5 |
| `GET /favorites` · `PUT /favorites/{perfumeKey}` · `DELETE /favorites/{perfumeKey}` | 찜 목록 · 찜(한도 300, 이미 있으면 그대로 성공) · 찜 풀기 | 필요 | D3 |
| `GET /feedback` · `POST /feedback` · `DELETE /feedback/{id}` | 시향 기록 목록 · 남기기(한도 1,000) · 본인 기록 지우기 | 필요 | D4 |
| `POST /events` | 사용 기록 묶음(최대 100개). 로그인했으면 user_id도 붙임 | 선택 | I1·I2 |
| `POST /reports` | 오류 신고(이름 오류·번역 안 된 노트 등). 새 표 `app.error_reports`(V2 마이그레이션) | 필요 | — (미뤄 둔 항목) |

- **서버에서 다시 검사(앱 검사를 믿지 않음):** 노트·향수 key는 **지금 카탈로그에 있는 것만**(서버가 시작할 때 카탈로그 파일을 읽어 key 목록을 메모리에 둠), 층당 3개·같은 노트 한 번·강도 weak/medium/strong, 이름 40자, 메모 500자, 만족도 1~5. DB 검사(V1)는 두 번째 그물.
- **동의 확인:** 쓰는 API(POST·PUT·DELETE, `/me/consents`·`DELETE /me` 제외)는 지금 버전의 세 동의가 다 있어야 받는다. 없으면 403 `CONSENT_REQUIRED`.
- **카탈로그 파일 자리:** 저장소에는 커밋하지 않으므로(라이선스) **Supabase Storage 공개 읽기 버킷 `catalog`**에 `catalog-<버전>.json.gz`로 올리고, 버전·해시·크기·최소 앱 버전은 새 표 `app.catalog_releases`(V2)에 둔다 → 미뤄 둔 "카탈로그 버전·최소 앱 버전 보관 방식"의 제안. 올리기는 사장 또는 직원이 `./gradlew` 작업 하나로(서비스 키 필요 → 이 컴퓨터 `.env`에서만).
- 앱용 TypeScript 타입은 서버의 OpenAPI 문서에서 만든다(springdoc + openapi-typescript).

## 3. 로그인 토큰 확인 방식
- Supabase 로그인 토큰(JWT)을 **Spring Security OAuth2 Resource Server**로 확인한다. 직접 해독 코드를 쓰지 않는다.
- 확인하는 것:
  | 항목 | 값 |
  |---|---|
  | 서명 | 프로젝트의 공개 키 목록(JWKS) `https://<참조값>.supabase.co/auth/v1/.well-known/jwks.json`으로 검사. **허용 알고리즘을 서버에 고정**(새 프로젝트 기본 비대칭 키 ES256 — 연결 뒤 실제 토큰 머리글로 확인). `none`·HS256은 거부 |
  | 발급자 `iss` | `https://<참조값>.supabase.co/auth/v1` |
  | 대상 `aud` | `authenticated` |
  | 만료 `exp` | 지났으면 거부(시계 오차 30초까지만 허용) |
  | `role` | `authenticated`만. `anon` 토큰(공개 키)으로는 로그인 API 불가 |
  | `is_anonymous` | true면 거부(익명 로그인은 쓰지 않음) |
- **로그아웃·계정 삭제 뒤 옛 토큰 막기(보안 규칙 1-2):** JWT는 만료(기본 1시간)까지 혼자 유효하다. 그래서 토큰의 `session_id`가 아직 살아 있는지 DB에서 확인한다 — `postgres` 소유 `security definer` 함수 `app.session_alive(session_id)`가 `auth.sessions`에 그 세션이 있는지만 돌려주고, `scent_server`에는 이 함수 실행만 준다(세션 표 자체는 못 읽음). 결과는 30초 동안 메모리에 보관. 로그아웃·계정 삭제 때 Supabase가 세션 줄을 지우므로 늦어도 30초 뒤 옛 토큰이 막힌다. (Supabase에서 postgres 계정이 `auth.sessions`를 읽을 수 있는지 **연결 뒤 확인**. 안 되면 예비안: 토큰 만료를 15분으로 줄이고 이 확인은 뺀다)
- 테스트: 가짜 JWKS를 띄워 서버 테스트에서 직접 만든 토큰으로 — 토큰 없음 401, 서명 다름 401, 알고리즘 none·HS256 401, 만료 401, aud 다름 401, anon 토큰 401, 세션 없음 401, 남의 조합 id 404.

## 4. 요청 횟수 제한 방식
- **Bucket4j(토큰 바구니) + 서버 메모리.** 서버가 1대라 메모리로 충분하다. 2대 이상이 되면 DB나 Redis로 옮긴다(그때 결정).
- 기준과 제안 값:
  | 대상 | 기준(누구 단위) | 제안 한도 | 넘으면 |
  |---|---|---|---|
  | 저장·찜·시향 기록·취향 바꾸기 (POST·PUT·DELETE) | 사용자 id | 분당 30회 | 429 `RATE_LIMITED` + `Retry-After` |
  | 취향 합치기 `merge` | 사용자 id | 분당 5회 | 429 |
  | 오류 신고 `POST /reports` | 사용자 id | 시간당 20회 | 429 |
  | 계정 삭제 `DELETE /me` | 사용자 id | 시간당 3회 | 429 |
  | 읽기 (GET) | 사용자 id | 분당 120회 | 429 |
  | 사용 기록 `POST /events` | install_id + IP | 분당 10회(한 번에 100개까지) | 429, 앱은 대기열에 두고 나중에 |
  | 로그인 없이 부르는 모든 것 (`/health`, `/catalog/latest`, 토큰 없는 `/events`) | IP | 분당 60회 | 429 |
  | 토큰 확인 실패(401)가 잦은 IP | IP | 분당 20회 실패 뒤 5분 막음 | 429 |
- IP는 올릴 곳의 프록시가 붙이는 `X-Forwarded-For`의 **맨 끝(프록시가 붙인 값)만** 믿는다(사용자가 앞에 아무 값이나 넣을 수 있음).
- 1인당 개수 한도(조합 100·찜 300·시향 기록 1,000)는 별개로, 그 사용자 단위 DB 잠금 안에서 세고 넣는다(동시에 20번 보내도 안 넘침, 서버 테스트로 확인).

## 5. 서버를 어디에 올릴지 (후보)
DB가 Supabase **서울**에 있어서, 서버도 가까울수록 저장·찜이 빠르다. 추천 계산은 앱 안이라 서버가 잠들어도 핵심 기능은 된다(E4 "서버를 깨우는 중이에요" 안내가 이미 승인 목록에 있음).

| 후보 | 무료로 쓸 때 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| **A. Render 무료 (추천)** — 싱가포르 지역 | 무료 웹 서비스, 15분 쉬면 잠듦(깨우는 데 30초~1분), 메모리 512MB (확인 필요) | **카드 등록 없이** 시작, GitHub 연결·Docker로 올리기가 가장 쉬움, design.md 16절의 원래 계획 | 잠듦 → 첫 저장이 느림. 서울 DB와 왕복 약 70ms(추정). Java가 512MB에 맞도록 메모리 상한 설정 필요 |
| B. Google Cloud Run — 서울 지역 | 매달 무료 사용량 안에서 0원, 요청 없으면 0대로 줄어듦(깨우는 데 수 초) (확인 필요) | DB와 같은 서울, 깨우기 빠름, 사용량만큼만 | **결제 카드 등록 필요**, 설정 화면이 복잡, 예산 알림·최대 1대 제한을 꼭 걸어야 함 |
| C. Fly.io | 무료 한도가 줄어 소액 과금 가능성 (확인 필요) | 도쿄 지역, 잠들지 않게 둘 수 있음 | 카드 필요, 요금 구조 변동 |
| D. Oracle Cloud 상시 무료 VM | 상시 무료 VM (확인 필요) | 잠들지 않음, 춘천·서울 지역 | 서버 관리(보안 업데이트·방화벽·HTTPS)를 직접 해야 함 → 초보에게 비추천, 보안 규칙상 인프라를 사장이 매번 확인해야 함 |

- **추천: A(Render, 싱가포르)로 시작.** 내부 테스트~초기 공개에는 잠듦이 불편한 정도이고 카드가 필요 없다. 사용자가 늘어 잠듦이 문제가 되면 Render 유료(월 약 7달러, 확인 필요) 또는 B(Cloud Run 서울)로 옮긴다. 서버는 Docker 이미지 하나라 옮기기가 쉽다.
- 어디로 가든: HTTPS만, DB 접속 정보·서비스 키는 그곳의 비밀 환경 변수에만, 열 포트는 서버 하나, 최대 대수 1, 메모리 상한(JVM `-XX:MaxRAMPercentage`). 올리는 일은 공개 작업이라 사장이 `!` 한 줄로.
- 서버가 생기면 일시 정지 방지 예약 작업이 `GET /health`를 부르게 바꾼다(서버도 하루 한 번 깨어남, DB까지 닿음).

## 6. 단계 4 순서 (승인 뒤 계획 모드에서 자세히)
1. Spring Boot 뼈대 + `/health` + 설정(.env 읽기) + 서버 테스트 틀(내장 Postgres 재사용, 가짜 JWKS)
2. 토큰 확인 + 세션 확인 + 요청 횟수 제한 + 오류 형식
3. 취향·합치기·동의 → 조합 → 찜 → 시향 기록 → 사용 기록 (각각 서버 테스트 먼저)
4. 계정 삭제(Supabase 관리 API) + 카탈로그 배포(V2: `catalog_releases`, `error_reports`) + 오류 신고
5. 리뷰(QA팀 + Gemini) → 레드팀(로그인·토큰·회원 파일이라 `.redteam-needed` 표시가 생김) → 올리기는 ★사장 결정 뒤
