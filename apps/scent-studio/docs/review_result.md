제공된 변경 사항을 리뷰한 결과, 보안 및 시스템 안정성 측면에서 몇 가지 중요한 개선 사항이 발견되었습니다.

### [심각도: 중간] Tomcat 스레드 고갈 위험 (동기화 블록 내 블로킹 I/O)
*   **파일명 및 줄 번호:** `CatalogController.java` (약 57-65행), `CatalogKeys.java` (약 81-100행)
*   **문제 이유:** `CatalogController.file` 메서드에서 `synchronized (files)` 블록 내부에 외부 스토리지로부터 파일을 가져오는 `store.fetch()` 호출이 포함되어 있습니다. `store.fetch()`는 최대 30초의 타임아웃을 가진 네트워크 I/O 작업입니다. 
    *   `application.yml` 설정상 Tomcat 최대 스레드가 16개로 매우 적은데, 한 스레드가 스토리로부터 대용량 카탈로그를 받는 동안 다른 모든 스레드(이미 캐시된 파일을 받으려는 요청 포함)가 해당 락을 기다리며 차단됩니다. 이는 서비스 전체의 응답 불가 상태(Thread Exhaustion)를 유발할 수 있습니다.
*   **수정 제안:** 네트워크 I/O 작업(`store.fetch`)을 동기화 블록 외부로 빼내야 합니다. `ConcurrentHashMap`과 `computeIfAbsent`를 사용하거나, 특정 버전에 대해서만 락을 거는 방식(Striped Locking)을 고려하십시오.

### [심각도: 중간] 대용량 파일 처리에 따른 Heap Memory 압박
*   **파일명 및 줄 번호:** `CatalogStore.java` (약 101행), `CatalogController.java` (약 44-49행)
*   **문제 이유:** 카탈로그 파일은 최대 50MB(`limit`)까지 허용됩니다. `store.fetch`에서 `in.readNBytes(limit + 1)`를 사용하여 전체 파일을 메모리(`byte[]`)에 로드하고, `CatalogController`에서 이를 최대 2개까지 캐싱합니다.
    *   Heap 메모리가 512MB(설계 문서 기준)인 상황에서, 여러 스레드가 동시에 파일을 처리하거나 캐시가 유지될 경우 GC 부하가 급증하거나 `OutOfMemoryError`가 발생할 위험이 있습니다.
*   **수정 제안:** 파일 전체를 `byte[]`로 들고 있기보다는, `InputStream`을 직접 스트리밍하며 SHA-256을 검증하고 클라이언트에게 전달하는 방식을 검토하십시오. 캐시가 꼭 필요하다면 오프힙(Off-heap) 메모리나 임시 파일 저장 방식을 고려하십시오.

### [심각도: 낮음] 쉘 스크립트 내 날짜 하드코딩
*   **파일명 및 줄 번호:** `api_check.sh` (약 44-45행)
*   **문제 이유:** 카탈로그 주소 확인 시 `catalog-2026.11.05.json.gz`와 같이 특정 날짜가 하드코딩되어 있습니다. 카탈로그 버전이 업데이트되면 이 체크 스크립트는 매번 수정되어야 하며, 그렇지 않으면 존재하지 않는 파일에 대한 잘못된 체크 결과를 반환하게 됩니다.
*   **수정 제안:** 현재 버전을 동적으로 조회하거나, 환경 변수 또는 인자로 버전을 전달받도록 수정하십시오.

### [심각도: 낮음] RateLimiter의 LRU 맵 동기화 성능
*   **파일명 및 줄 번호:** `RateLimiter.java` (약 78-83행)
*   **문제 이유:** `LinkedHashMap`을 사용하여 LRU 캐시를 구현하고 `synchronized` 블록으로 보호하고 있습니다. 16개 스레드 환경에서는 큰 문제가 아닐 수 있으나, 모든 요청이 해당 락을 거쳐야 하므로 경합이 발생할 수 있습니다.
*   **수정 제안:** Java 표준 라이브러리에는 스레드 안전한 LRU 맵이 없으므로 현재 방식도 허용 가능하지만, 향후 성능 확장이 필요하다면 Caffeine 같은 전문 캐시 라이브러리 도입을 권장합니다.

**그 외 `EventsController.java`의 데이터 검증(NUL 문자 및 Surrogate Pair 체크 등)과 `CatalogStore.java`의 보안 키 패턴 체크는 매우 적절하게 구현되었습니다.**
