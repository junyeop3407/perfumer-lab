## 1. 카탈로그: 엔진 6 → 엔진 8 교체, 그리고 실제/샘플 고르기

### 1-1. 지금 상태
- 앱은 `app/assets/catalog/catalog.json.gz`(커밋 안 함)를 앱 안에 넣어 쓴다(오프라인 추천, 승인 E2). 서버의 `/catalog/latest`·`/catalog/{version}`은 **더 새 버전이 있을 때 받는 길**이다(묶음 6).
- 기록상 앱 안 파일은 옛 2026.10.31(엔진 6)이었다(남은 것 7). **이 Windows 컴퓨터에서는 `build_catalog.py`가 같이 써서 이미 2026.11.05(엔진 8)** 이다(해시가 배포본과 같음, 2026-11-11 확인). 다른 컴퓨터는 다를 수 있으니 아래 절차로 맞춘다.

### 1-2. 실제 카탈로그 받기 (비공개 버킷 → 앱)
- 새 운영 도구 `./gradlew dbCatalogFetch`(backend `DbOps`, `dbCatalogPublish`와 같은 곳)를 만든다. 동작:
  1. `.env`의 서버 전용 키로 비공개 버킷 `catalog`에서 `catalog_releases`의 **지금 버전** 파일을 받는다.
  2. `catalog_releases`의 sha256·크기와 비교한다. 다르면 멈춘다.
  3. `app/assets/catalog/catalog.json.gz`에 쓴다.
- 키는 출력하지 않는다. 받은 파일은 커밋하지 않는다(`.gitignore` 그대로).
- 서버 공개 주소(`/catalog/{version}`)는 쓰지 않는다. 설치 id당 하루 3회 제한이 있고, 앱용이기 때문이다.
- 테스트: 가짜 Storage로 "해시 같음 → 씀 / 다름 → 안 씀 / 버전 없음 → 멈춤"(서버 테스트 방식 그대로).

### 1-3. 샘플 카탈로그 (Plan B 데모, 가상 브랜드)
- 새 생성기 `pipeline/sample_catalog.py`를 만든다. **실제 데이터 파일을 하나도 읽지 않는다.**
  - 노트: 우리가 만든 `pipeline/manual/notes_ko.csv`의 이름·한글명만 쓴다(일반 단어). 앱 목록에 필요한 만큼(약 150개)만 쓴다.
  - 노트 프로필(어코드 비율): **실제 데이터에서 계산한 값은 쓰지 않는다.** 계열별 기본 비율(직접 정함, 문서화)에 고정 난수로 작은 흔들림을 줘서 새로 만든다.
  - 향수: 가상 브랜드 **20개** × 향수 **300개**. 이름은 누가 봐도 가짜인 이름(예: `Demo Atelier — Sample No. 12`, `Placeholder Parfums — Test Cedar`). 계열별 노트 조합으로 만들고, 어코드는 노트 프로필 평균으로 계산한다. 평점·평가 수도 지어낸 값이다.
  - 형식: 엔진 8 카탈로그와 **같은 칸**이다(`accordShares`·`noteWeights` 포함). `source = {"name": "sample", "note": "가상 데이터"}`.
- 확인(테스트 먼저):
  - 형식이 실제 카탈로그와 같다(칸 이름·형).
  - 고정 난수로 다시 만들면 바이트까지 같다.
  - 실제 브랜드 목록·`parfumo.com`·실제 향수 key 모양이 하나도 없다.
  - TS 엔진으로 추천이 돈다.
  - 맹점·재현 같은 엔진 기준은 샘플에서는 재지 않는다. 데모용이라 "그럴듯함"만 확인한다.
- 생성 결과는 커밋하지 않는다(빌드할 때 만든다). 생성기와 그 테스트는 커밋한다.

### 1-4. 빌드할 때 고르기
- 환경 변수 `CATALOG_SOURCE=real|sample`과 준비 스크립트 `app/scripts/prepare-catalog.mjs`를 둔다. `expo export`·`expo prebuild` 앞에 돈다.
  - **자리를 나눈다(사장 결정 2026-11-11)**: 실제 `catalog.real.json.gz`(+ 받기 기록 `catalog.real.release.json`), 샘플 `catalog.sample.json.gz`, 이번 빌드 자리 `catalog.json.gz`(폰) · `app/public/catalog.json.gz`(웹). 고른 쪽을 빌드 자리에 복사하므로 바꿀 때마다 다시 받을 필요가 없다. 모두 `.gitignore`(테스트 `catalogIgnore.test.ts`가 `git check-ignore`로 확인).
  - `real`: `catalog.real.json.gz`가 있고, `source.name`이 sample이 아니고, 해시가 받기 기록(`catalog_releases`)과 같은지 확인한다. 없으면 `dbCatalogFetch` 안내를 내고 멈춘다.
  - `sample`: `sample_catalog.py`로 `catalog.sample.json.gz`를 만들고(같은 seed라 매번 같은 바이트) 실제 이름 검사 뒤 복사한다.
- **공개 데모 빌드(Plan B Pages)는 `sample`만 허용한다.** 빌드 결과물에 실제 **브랜드·향수 이름**이 하나라도 있으면 실패한다(2-9와 같이 돈다).
  - **실제 이름 목록은 공개 저장소에 두지 않는다**(사장 조건). 방법: 비공개 카탈로그에서 만든 **해시 목록**만 쓴다.
    - 브랜드·향수 이름을 소문자·공백 정리한 뒤 `SCENT_KEY_SECRET`을 섞은 HMAC-SHA256으로 바꾼다. 지금 정리 목록(`filtered_keys.csv`)과 같은 방식이다.
    - 그 목록은 `pipeline/data/out/real_name_hashes.txt`(커밋 안 함)에 둔다.
  - 검사: 빌드 결과물의 글자 조각(브랜드 칸·이름 칸, 그리고 2~6단어 묶음)을 같은 방식으로 해시해 목록과 겹치면 실패.
  - **해시 목록이나 키가 없는 컴퓨터에서는 이 검사를 "건너뜀"으로 표시**한다(Mac 파이프라인과 같은 방식). 공개 빌드 전 최종 검사는 키가 있는 컴퓨터에서 돌린다.
  - 해시 목록 자체도 공개하지 않는다. 키를 섞으므로 공개돼도 이름을 되돌리기 어렵지만, 그래도 커밋하지 않는다.
- 앱은 `source.name`을 보고 "가상 데이터" 표시를 한다(출처 화면 문구는 `plan_b_portfolio.md` 1-7).
- 승인 테스트는 지금처럼 `tests/fixtures/test_catalog.json.gz`(합성)를 쓴다. 실제·샘플과 상관없다.

### 8-6. 방법
1. **Expo Go로 실제 폰 확인** — 가장 빠르다. `cd app && npx expo start` → 폰의 Expo Go로 QR을 찍는다. 폰과 컴퓨터는 같은 와이파이(회사·공용 와이파이처럼 막히면 `npx expo start --tunnel`). 코드를 고치면 바로 바뀐다.
2. **안드로이드 에뮬레이터** (Windows·Mac) — Android Studio → Device Manager에서 기기 2개를 만든다(① 360×800dp, ② 412×915dp). `npx expo start` 뒤 `a`. 글자 크기·다크 모드·내비게이션 방식은 에뮬레이터 설정에서, 느린 네트워크는 에뮬레이터 확장 설정(Cellular)에서 바꾼다.
3. **iOS 시뮬레이터 (Mac 필요)** — Xcode를 깔고 iPhone SE(3세대)·iPhone 16 Pro 시뮬레이터를 받는다. `npx expo start` 뒤 `i`. 글자 크기는 시뮬레이터 설정 → 손쉬운 사용, 또는 Xcode의 Environment Overrides. **키보드·한글 입력은 시뮬레이터보다 실기기가 정확**하다(D3·D4는 실기기로 최종).
4. **자동 흐름 테스트: Maestro 추천**
   - 이유: 흐름을 짧은 YAML로 쓰고(예: 앱 열기 → 노트 3개 → 요약 → 추천 → 상세 → 뒤로), Expo Go·개발용 빌드·안드로이드 에뮬레이터·iOS 시뮬레이터에서 **같은 파일**을 돌린다. 화면의 testID(`app/src/ui/testIds.ts`)를 그대로 쓴다. 단계마다 캡처를 남긴다. Detox보다 준비가 가볍다(앱 빌드에 테스트 코드를 넣지 않음).
   - 자동으로 맡길 것: D1(열림)·D5(뒤로)·D9(돌려도 세로)·D10 일부(비행기 모드로 추천)·기본 흐름 캡처. 다크 모드·글자 크기는 명령(`adb shell settings put system font_scale 2.0` 등)으로 바꾼 뒤 캡처.
   - 사람 눈으로 볼 것: D2(가림)·D3(키보드)·D4(한글 조합)·D6(글꼴 깜빡임)의 최종 판단.
   - 한계: 아이폰은 Mac에서만(Windows는 안드로이드만, 설치 때 다시 확인). 클라우드 실행은 유료라 로컬만 쓴다. 에뮬레이터가 필요하고 오래 걸려 `tests/run.sh`에는 넣지 않고 5-8·5-9에서 따로 돌린다(`app/tests/maestro/`).

### 8-7. Expo Go로 안 되는 것(또는 결과가 다른 것) → 개발용 빌드가 필요
| 기능 | Expo Go에서 | 언제 개발용 빌드로 |
|---|---|---|
| 세로 고정(D9) | Expo Go 앱의 화면 회전 설정을 따라 실제 앱과 다를 수 있다(확인 필요) | 5-9 최종 |
| 구글 로그인 후 앱으로 돌아오기(딥링크) | 주소가 `exp://…`라 실제 앱 `perfumerlab://`과 다르다. Supabase Redirect URLs에 Expo Go 주소를 따로 넣어야 한다 | 5-5 실제 로그인 확인은 개발용 빌드 권장 |
| 앱 아이콘·스플래시·앱 이름·안드로이드 적응형 아이콘 | Expo Go 것이 보인다 | 5-9 |
| 안드로이드 내비게이션 바 색·뒤로 가기 설정(`predictiveBackGestureEnabled`) | 앱 설정이 적용되지 않을 수 있다 | 5-8 끝~5-9 |
| SDK 버전 | Expo Go는 최신 SDK 하나만 지원한다. 폰의 Expo Go가 우리 SDK(58)와 다르면 열리지 않는다 | 그때 바로 |
| 성능(D11) | 개발 모드라 느리다 | 미리 보기(릴리스) 빌드로 잰다 |
| 카카오 로그인(보류) | 네이티브 SDK를 쓰면 불가 | 카카오 재시작 때 |

- 결론: **5-2~5-7은 Expo Go + 에뮬레이터로 충분**, **5-8 끝~5-9는 개발용 빌드**. 빌드 방식(EAS Build 무료 한도 vs 로컬 `npx expo run:android`·Xcode)은 "안드로이드 빌드 방식 11-25 뒤 결정"(4-2)과 같이 정한다.
