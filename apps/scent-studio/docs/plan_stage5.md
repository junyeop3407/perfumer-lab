## 1. 카탈로그: 엔진 6 → 엔진 8 교체, 그리고 실제/샘플 고르기

### 1-1. 지금 상태
- 앱은 `app/assets/catalog/catalog.json.gz`(커밋 안 함)를 앱 안에 넣어 쓴다(오프라인 추천, 승인 E2). 서버의 `/catalog/latest`·`/catalog/{version}`은 **더 새 버전이 있을 때 받는 길**이다(묶음 6).
- 기록상 앱 안 파일은 옛 2026.10.31(엔진 6)이었다(남은 것 7). **이 Windows 컴퓨터에서는 `build_catalog.py`가 같이 써서 이미 2026.11.05(엔진 8)** 이다(해시가 배포본과 같음, 2026-11-11 확인). 다른 컴퓨터는 다를 수 있으니 아래 절차로 맞춘다.

### 1-2. 실제 카탈로그 받기 (비공개 버킷 → 앱)
- 새 운영 도구 `./gradlew dbCatalogFetch`(backend `DbOps`, `dbCatalogPublish`와 같은 곳)를 만든다. 동작:
  1. `.env`의 서버 전용 키로 비공개 버킷 `catalog`에서 `catalog_releases`의 **지금 버전** 파일을 받는다.
  2. `catalog_releases`의 sha256·크기와 비교한다. 다르면 멈춘다.
  3. `app/assets/catalog/catalog.json.gz`에 쓴다.
- 키는 출력하지 않는다. 받은 파일은 커밋하지 않는다(`.gitignore` 그대로).
- 서버 공개 주소(`/catalog/{version}`)는 쓰지 않는다. 설치 id당 하루 3회 제한이 있고, 앱용이기 때문이다.
- 테스트: 가짜 Storage로 "해시 같음 → 씀 / 다름 → 안 씀 / 버전 없음 → 멈춤"(서버 테스트 방식 그대로).

### 1-3. 샘플 카탈로그 (Plan B 데모, 가상 브랜드)
- 새 생성기 `pipeline/sample_catalog.py`를 만든다. **실제 데이터 파일을 하나도 읽지 않는다.**
  - 노트: 우리가 만든 `pipeline/manual/notes_ko.csv`의 이름·한글명만 쓴다(일반 단어). 앱 목록에 필요한 만큼(약 150개)만 쓴다.
  - 노트 프로필(어코드 비율): **실제 데이터에서 계산한 값은 쓰지 않는다.** 계열별 기본 비율(직접 정함, 문서화)에 고정 난수로 작은 흔들림을 줘서 새로 만든다.
  - 향수: 가상 브랜드 **20개** × 향수 **300개**. 이름은 누가 봐도 가짜인 이름(예: `Demo Atelier — Sample No. 12`, `Placeholder Parfums — Test Cedar`). 계열별 노트 조합으로 만들고, 어코드는 노트 프로필 평균으로 계산한다. 평점·평가 수도 지어낸 값이다.
  - 형식: 엔진 8 카탈로그와 **같은 칸**이다(`accordShares`·`noteWeights` 포함). `source = {"name": "sample", "note": "가상 데이터"}`.
- 확인(테스트 먼저):
  - 형식이 실제 카탈로그와 같다(칸 이름·형).
  - 고정 난수로 다시 만들면 바이트까지 같다.
  - 실제 브랜드 목록·`parfumo.com`·실제 향수 key 모양이 하나도 없다.
  - TS 엔진으로 추천이 돈다.
  - 맹점·재현 같은 엔진 기준은 샘플에서는 재지 않는다. 데모용이라 "그럴듯함"만 확인한다.
- 생성 결과는 커밋하지 않는다(빌드할 때 만든다). 생성기와 그 테스트는 커밋한다.

### 1-4. 빌드할 때 고르기
- 환경 변수 `CATALOG_SOURCE=real|sample`과 준비 스크립트 `app/scripts/prepare-catalog.mjs`를 둔다. `expo export`·`expo prebuild` 앞에 돈다.
  - `real`: `app/assets/catalog/catalog.json.gz`가 있고, `source.name`이 sample이 아니고, 해시가 `catalog_releases`와 같은지 확인한다. 없으면 `dbCatalogFetch` 안내를 내고 멈춘다.
  - `sample`: `sample_catalog.py`로 만들어 같은 자리에 둔다.
- **공개 데모 빌드(Plan B Pages)는 `sample`만 허용한다.** 빌드 결과물에 실제 **브랜드·향수 이름**이 하나라도 있으면 실패한다(2-9와 같이 돈다).
  - **실제 이름 목록은 공개 저장소에 두지 않는다**(사장 조건). 방법: 비공개 카탈로그에서 만든 **해시 목록**만 쓴다.
    - 브랜드·향수 이름을 소문자·공백 정리한 뒤 `SCENT_KEY_SECRET`을 섞은 HMAC-SHA256으로 바꾼다. 지금 정리 목록(`filtered_keys.csv`)과 같은 방식이다.
    - 그 목록은 `pipeline/data/out/real_name_hashes.txt`(커밋 안 함)에 둔다.
  - 검사: 빌드 결과물의 글자 조각(브랜드 칸·이름 칸, 그리고 2~6단어 묶음)을 같은 방식으로 해시해 목록과 겹치면 실패.
  - **해시 목록이나 키가 없는 컴퓨터에서는 이 검사를 "건너뜀"으로 표시**한다(Mac 파이프라인과 같은 방식). 공개 빌드 전 최종 검사는 키가 있는 컴퓨터에서 돌린다.
  - 해시 목록 자체도 공개하지 않는다. 키를 섞으므로 공개돼도 이름을 되돌리기 어렵지만, 그래도 커밋하지 않는다.
- 앱은 `source.name`을 보고 "가상 데이터" 표시를 한다(출처 화면 문구는 `plan_b_portfolio.md` 1-7).
- 승인 테스트는 지금처럼 `tests/fixtures/test_catalog.json.gz`(합성)를 쓴다. 실제·샘플과 상관없다.
