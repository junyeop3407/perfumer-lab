## 1. 배합이 공개되지 않아 향을 숫자로 정확히 나타낼 수 없음

**문제.** 조합을 추천하려면 향을 숫자로 바꿔야 합니다. 하지만 향수의 실제 배합은 공개되지 않습니다. 처음 쓴 Parfumo 데이터(59,325개)에도 어코드 이름만 있고 비율은 없었습니다.

**첫 대응과 한계.** 어코드 목록이 진한 순서라고 가정하고 5·4·3·2·1 비중을 줬습니다. 나중에 실제 강도와 비교하니 5위 어코드를 절반쯤 낮게 잡고 있었습니다(실제 13.3%, 추정 6.7%). 노트 강도 정보도 없어서, 고른 노트가 살짝 들어간 향수와 주인공인 향수를 구분하지 못했습니다.

**해결.** Fragrantica 사용자가 투표한 어코드·노트 강도를 가져왔습니다.

- 공식 API가 없고 약관 문제가 있어 사이트를 직접 수집하지 않고, 공개 데이터셋 Decant를 썼습니다.
- 사이트마다 표기가 달라 브랜드·이름으로 찾은 뒤 노트가 30% 이상 겹칠 때만 연결했습니다. 이름이 맞는 8,437개 중 6,961개(후보의 51.7%)가 연결됐습니다.
- Fragrantica 어코드 92개를 앱의 21개로 묶는 연결표를 CSV로 분리해 직접 검토했습니다.
- 처음 설계한 Tversky 식은 시험해 보니 층 정보를 잃어 재현이 떨어졌습니다. 그래서 기존 일치도에 강도 몫을 곱하는 식으로 바꿨습니다.

```
노트 일치도 = 기본 일치도 × (0.3 + 0.7 × √강도 몫 합)
```

**결과.** "비슷하다"는 투표를 받은 향수가 Top 50에 오는 비율이 38.4%에서 44.3%로 올랐습니다(+5.9%p, 95% 구간 +2.6~+8.9, 시험판을 고를 때 쓰지 않은 쿼리 461개). 비교 조합 Top 10의 노트 수 중앙값은 11개에서 9개로 줄어 노트가 많은 향수가 유리하던 문제도 줄었습니다.

**남은 한계.** 이 강도는 실제 함량이 아니라 **사람이 느낀 강도**입니다. 배합을 알아낸 것이 아니라 더 나은 대리 지표를 찾은 것이고, 앱 화면에도 그렇게 밝힐 계획입니다. 새로 생긴 문제는 "아직 풀지 못한 문제"에 적었습니다.

## 2. Fragrantica 데이터의 배포 조건

**문제.** 1번의 해결이 새 문제를 만들었습니다. Fragrantica 약관상 정보를 가져와 배포하려면 허가가 필요합니다. Decant도 Kaggle 표기가 CC BY-NC-SA 4.0이라 비상업·출처 표시·동일 조건 공유를 지켜야 합니다.

**대응.**

- Fragrantica에 허가를 요청하는 메일을 보냈고 회신을 기다립니다.
- 비상업 무료 앱으로 운영합니다.
- 처음에는 회신 전까지 초대한 사람만 쓰는 내부 테스트로 제한하려 했고, 초대 목록 표와 가입 직전 검사까지 설계했습니다. 하지만 비상업 무료 앱이라 허가 가능성이 높다고 보고, **허가를 전제로 초대제 없이 공개 배포 기준으로 개발하기로 바꿨습니다**(2026-11-06). 초대제가 하던 "모르는 사람 차단"이 빠지는 만큼 사용자별 요청 횟수 제한과 1인당 저장 한도로 무료 요금제를 지킵니다.
- 대신 **실제 스토어 공개는 회신을 받은 뒤**에 하도록 출시 직전 확인 항목에 넣었습니다. 개발 순서는 그대로 두고, 공개 시점만 회신에 묶었습니다.
- 받은 원본과 카탈로그는 공개 저장소에 커밋하지 않습니다.
- 화면에 출처를 표시하기로 했습니다.

**아직 해결되지 않은 것.** 회신을 받지 못했고, 거절되면 강도 데이터를 빼거나 다른 출처를 찾아야 합니다. 엔진은 강도 없는 향수도 계산할 수 있지만, 그 경우 1번의 성능 개선을 잃습니다. Parfumo 데이터도 라이선스 표시가 없어 정식 공개 전에 따로 확인해야 합니다.

## 3. 노트를 다 넣어도 그 향수를 못 찾음

**문제.** 향수의 노트를 그대로 넣었는데 그 향수가 Top 3에 나오지 않았습니다. 처음 정한 어코드 60 : 노트 30에서는 20개 중 9개만 성공했습니다.

**원인.** 실패한 향수는 노트 일치도가 1.000인데 어코드 유사도가 0.40~0.54였습니다. 노트로 계산한 어코드와 커뮤니티가 붙인 어코드가 달라, 노트를 다 맞혀도 밀렸습니다.

**해결.** 실제 데이터로 비교하며 가중치를 바꿨습니다.

| 어코드 : 노트 | 재현 (20개) | 재현 (100개) |
|---:|---:|---:|
| 60 : 30 | 9 | |
| 45 : 45 | 15 | 87 |
| 35 : 55 | 17 | 96 |

이후 노트 프로필 계산을 고치고 복사 오류(4번)를 빼서 지금은 20/20입니다. 다만 복사 오류를 빼면서 정답 향수 일부도 바뀌었으므로, 이 증가가 모두 엔진 개선 덕분은 아닙니다.

## 4. 원본 데이터의 복사 오류

**문제.** 재현 시험에 실패한 향수를 살펴보니, 브랜드가 다른 향수들의 노트·평가 수·어코드가 똑같았습니다. 2007년에 창업한 브랜드의 향수가 1983년 출시로 적혀 있기도 했습니다.

**원인.** 처음에는 클론 향수인지 의심했습니다. 하지만 무작위 20개를 확인하니 17개가 수집 오류로 보였습니다. 이름·브랜드·주소는 각자 것이고 상세 정보만 다른 향수 것이 들어간 형태였습니다. 우리 코드가 아니라 외부 데이터셋의 문제이고, 파일 전체에 고르게 흩어져 있었습니다.

**해결.** 브랜드가 다른데 노트·평가 수·평점·어코드·조향사가 모두 같으면 복사로 봅니다. 조향사의 이력과 브랜드의 역사로 원본을 가릴 수 있으면 원본만 남기고, 못 가리면 묶음째 뺍니다. 평가 수나 어코드가 다른 묶음은 진짜 클론일 수 있어 남겼습니다.

**결과.** 333개를 후보에서 뺐습니다. 데이터를 지우지 않고 사유와 함께 기록으로 남겨 다시 검토할 수 있습니다.

## 5. 다른 향수가 같은 향수로 묶임

**문제.** 추천에서는 농도만 다른 같은 향수를 하나만 보여 줍니다. 그런데 Joop! Homme 1989년판이 노트가 전혀 다른 2021년판에 가려졌습니다.

**원인.** 묶음 값이 이름에서 연도를 지운 것이었습니다. 여러 버전이 있는 502묶음 중 300묶음은 노트 겹침이 0.5 미만이었습니다.

**해결.** 이름이 같은 묶음 안에서 평가가 많은 순으로 보며, 대표 향수와 노트가 0.5 이상 겹칠 때만 같은 묶음으로 뒀습니다. 회귀 테스트를 먼저 넣어 실패를 확인한 뒤 고쳤습니다. 노트가 100% 같은 Mediterraneo 세 버전은 그대로 한 묶음입니다.

## 6. 정답이 없는 추천을 어떻게 검증할까

**문제.** 엔진은 향을 맡지 못하고 저도 후보 수천 개를 시향할 수 없습니다. 재현 시험은 금방 20/20이 되어, 노트를 줄인 어려운 버전까지 더 이상 엔진 차이를 가려내지 못했습니다.

**해결.** 성격이 다른 시험을 나눠 쌓았습니다.

| 시험 | 확인하는 것 | 기준 | 지금 |
|---|---|---:|---:|
| 재현 | 향수의 노트를 넣으면 그 향수를 찾는가 | 15/20 | 20/20 |
| 맹점 | 특정 어코드가 사라지지 않는가 | 4/5 | 4/5 |
| 다양성 | 일부 브랜드로 쏠리지 않는가 | 40개 | 92개 |
| 사람 유사 | 사람이 비슷하다고 투표한 향수를 찾는가 | v6보다 높음 | 44.3% (v6 38.4%) |
| 블라인드·눈으로 평가 | 사람이 볼 때 더 나은가 | 8/12, 평균 3.5 | **답 대기** |

**결과를 속이지 않으려고 한 일.**

- 사람 유사 시험은 개발 절반으로 후보를 고르고, 남겨 둔 절반으로 확인했습니다. 추천 조건도 남겨 둔 절반을 보기 전에 정했습니다.
- 어떤 후보도 이 투표를 계산에 쓰지 않습니다.
- 블라인드는 A/B를 고정 난수로 섞고, 문서가 실수로 다시 만들어지지 않게 막았습니다. 두 목록의 향수가 같아 판별력이 없는 줄은 따로 표시합니다.
- 비교 조합은 결과를 보기 전에 적은 후보에서, 어느 쪽이 좋아 보이는지가 아니라 다른 향수의 수로만 골랐습니다.
- AI가 시향 없이 매긴 임시 답(9.5/10)은 판정에 쓰지 않고 보관만 합니다.

**한계.** 사람 유사 시험의 정답도 사람들의 인식이고, 블라인드도 시향이 아니라 이름과 어코드를 보고 판단합니다. 실제 향이 비슷하다는 증명은 아닙니다.

## 7. DB 설계가 정규화 원칙과 어긋남

**문제.** 사용자 데이터 표 5개를 설계하면서, 저장한 조합의 노트 목록(`blends.notes`)을 JSON 한 칸에, 선호 계열과 불호 노트(`user_preferences`)를 배열 한 칸에 담는 안이 나왔습니다. 수업에서 배운 제1정규형은 "한 칸에는 값 하나"이므로 이 안은 원칙과 어긋납니다. 면접에서 "왜 정규화하지 않았나요?"라는 질문을 받을 수 있는 부분이라, 그대로 넘기지 않고 따져 봤습니다.

**비교한 두 안.**

| | 정규화한 안 | 선택한 안 |
|---|---|---|
| 구조 | `blend_notes` 표를 따로 두고 노트 하나당 한 줄 (조합 id, 노트 key, 층, 강도) | `blends.notes`에 `[{note_key, layer, strength}]`를 JSON으로 |
| 조합 하나 읽기 | 두 표를 조인 | 한 줄만 읽음 |
| 조합 고치기 | 노트 줄을 지우고 다시 넣기, 트랜잭션 필요 | 한 칸 교체 |
| 무결성 | 외래 키·유일 키로 자연스럽게 | DB 검사 함수를 따로 만들어야 함 |
| "이 노트를 쓴 조합" 같은 검색 | 쉬움 | 어려움 |

**판단 근거.**

- **데이터를 쓰는 방식**: 조합은 항상 통째로 저장하고 통째로 다시 엽니다. 노트 하나만 따로 고치거나 꺼내는 기능이 없습니다.
- **크기**: 한 조합의 노트는 최대 9개(층마다 3개)라 작고 상한이 정해져 있습니다.
- **검색 필요 없음**: 추천 계산은 서버 DB가 아니라 앱 안 엔진이 합니다. "어떤 노트가 많이 쓰였나" 같은 통계는 사용 기록 표에서 봅니다.
- 그래서 정규화했을 때 얻는 장점(부분 수정, 노트 단위 검색)을 쓸 곳이 없고, 조인과 트랜잭션 비용만 남습니다.
- 반대로 정규화가 필요한 곳은 그대로 지켰습니다. 찜(`favorites`)은 (사용자, 향수 key) 복합 기본 키로 중복을 막고, 시향 기록은 (조합 id, 사용자 id) 묶음 외래 키로 남의 조합을 연결하지 못하게 했습니다.

**해결.**

- **조합 노트는 JSON 한 칸, 선호·불호는 배열 한 칸으로 두기로 결정했습니다.** 원칙을 모르고 어긴 것이 아니라, 쓰임새를 보고 고른 의도된 예외입니다.
- **정규화가 해 주던 무결성은 DB 검사로 대신했습니다.** 노트 1~9개, 층은 top/middle/base만, 층마다 3개까지, 같은 노트 한 번만, 강도는 weak/medium/strong만 들어가도록 DB 검사 함수로 막고, 잘못된 값(층에 노트 4개, 같은 노트 두 번, 모르는 강도 등)이 실제로 막히는지 테스트 DB 검사 항목에 넣었습니다.
- **나중에 바꿀 조건을 정해 뒀습니다.** 노트 단위 검색이나 부분 수정 기능이 생기면 `blend_notes` 표로 나눕니다. JSON 구조가 표의 칼럼과 1:1이라 옮기기 쉽습니다.
- **이유를 설계 문서(design.md)에 남기도록 했습니다.** 결정과 근거, 바꿀 조건을 문서로 남겨 누가 봐도 왜 이렇게 했는지 알 수 있게 했습니다.

# 앱을 만들면서 배우고 느낀 점

처음으로 바이브 코딩(AI에게 말로 지시해 코드를 만드는 방식)을 활용해 하나의 앱을 기획부터 구현까지 완성했다.

이번 프로젝트를 진행하면서 가장 크게 느낀 점은 **코드를 만드는 것보다 작업 규칙을 정하고, 구조를 설계하고, 데이터 사용 가능 여부를 확인하는 과정이 더 중요할 수 있다는 것**이었다.

특히 AI에게 작업을 맡기더라도 결과를 검토하고 방향을 결정하는 것은 결국 사람의 역할이라는 점을 경험했다.

## 프로젝트를 진행하며 경험한 것

| 구분 | 내용 |
|---|---|
| 개발 방식 | Claude Code를 활용한 바이브 코딩 |
| Frontend | Expo (Web / Android / iOS) |
| Backend | Java Spring |
| Database / Auth | Supabase |
| 협업 방식 | AI를 활용한 계획, 구현, 테스트 및 교차 리뷰 |
| 결과물 | 앱 구현 완료, GitHub 코드 공개, 샘플 데이터 기반 데모 구성 |

## 가장 크게 배운 점 3가지

**1. AI에게 작업을 맡기기 전에 명확한 규칙이 필요했다.**

단순히 기능을 요청하는 것만으로는 의도한 결과를 얻기 어려웠다. 작업 단계별 승인, 테스트 실패 시 커밋 방지, 보안 검사, 교차 리뷰 등 작업 기준을 직접 정리했다. 진행하면서 발견한 문제도 규칙에 계속 반영했다.

**2. 프롬프트와 초반 설계가 결과에 큰 영향을 줬다.**

작업 범위, 중단 시점, 보고 형식, 금지 사항 등을 구체적으로 전달해야 했다. 또한 설계안을 비교하고 테스트 목록을 먼저 정한 다음 구현하는 방식이 불필요한 수정을 줄이는 데 도움이 됐다.

**3. 데이터 사용 권한은 개발 전에 확인해야 했다.**

향수 데이터를 수집하는 과정에서 데이터 수집이 가능하다는 것과 실제 서비스에서 사용할 수 있다는 것은 다르다는 점을 알게 됐다. 사이트에 사용 허가를 요청했지만 답변을 받지 못해 기존 수집 데이터로는 스토어 배포를 진행하지 않았다.

---

## 1. AI와 함께 작업하기 위한 규칙 만들기

이번 프로젝트에서는 Claude Code와 역할을 나누어 진행했다.

나는 무엇을 만들지 결정하고 결과를 검토했으며, AI는 계획 수립부터 구현과 테스트까지 담당하는 방식이었다.

처음에는 AI가 작업을 잘 수행하도록 지시하는 데 집중했지만, 프로젝트가 길어지면서 일관된 작업 기준이 필요하다고 느꼈다.

강의와 여러 자료에서 접한 개발 방법에 내 기준을 더해 규칙 문서를 만들었다.

- 각 단계가 끝나면 다음 단계로 넘어가기 전에 승인받기
- 테스트 실패 또는 비밀값 포함 시 커밋 차단하기
- 레드팀 방식으로 보안 취약점 확인하기
- Claude와 Gemini를 활용해 서로 다른 관점에서 코드 리뷰하기

규칙을 처음부터 완벽하게 만든 것은 아니다. 실제 작업 중 발견한 문제를 바탕으로 계속 보완하고 있다.

예를 들어 필요한 도구가 없는 상황에서 AI가 임의로 다른 방법을 사용해 작업을 진행한 적이 있었다. 이후에는 필요한 도구가 없으면 임의로 대체하지 않고 작업을 멈춘 뒤 설치를 요청하도록 규칙을 추가했다.

이 경험을 통해 AI에게 작업을 맡기는 것뿐만 아니라, 어떤 상황에서 진행하고 어떤 상황에서 멈춰야 하는지를 정하는 것도 중요하다는 것을 배웠다.

## 2. 프롬프트 작성과 초반 설계의 중요성

처음에는 원하는 기능을 설명하면 나머지는 AI가 알아서 처리할 것이라고 생각했다.

하지만 요청이 모호하면 AI가 빈 부분을 추측해서 구현했고, 그 결과 의도하지 않은 방향으로 작업이 진행되기도 했다.

이후 프롬프트에 다음 내용을 구체적으로 포함하려고 했다.

- 작업할 범위와 목적
- 작업을 멈추고 보고해야 하는 시점
- 결과를 보고할 형식
- 진행하면 안 되는 작업이나 변경 사항

또한 한 번에 모든 작업을 진행하기보다는 단계별로 결과를 보고받고, 내용을 확인한 다음 다음 작업을 요청하는 방식을 사용했다.

설계에서도 비슷한 문제를 경험했다. 초반에 정한 프로젝트 구조가 이후 구현의 기준이 되기 때문에 충분히 검토하지 않고 시작하면 나중에 수정해야 하는 범위가 커졌다.

그래서 현재는 다음 순서를 기준으로 작업하고 있다.

1. 여러 설계안을 비교하고 방향 결정하기
2. 필요한 테스트 목록을 작성하고 승인받기
3. 승인된 내용을 바탕으로 구현하기

이 과정을 반복하면서 프롬프트는 단순히 원하는 것을 설명하는 문장이 아니라 작업의 범위와 방향을 정하는 지시서에 가깝다고 느꼈다.

## 3. 데이터 사용 권한 문제와 대응

이번 프로젝트에서 가장 예상하지 못했던 문제는 코드 구현이 아닌 데이터 사용 권한이었다.

향수 추천 기능을 만들기 위해 해외 향수 정보 사이트인 Parfumo와 Fragrantica에서 데이터를 수집했다.

처음에는 무료로 앱을 배포한다면 큰 문제가 없을 것이라고 생각했지만, 개발 도중 무료 배포 여부와 관계없이 사이트의 이용약관과 데이터 사용 허가를 확인해야 한다는 것을 알게 됐다.

두 사이트에 사용 허가 요청 메일과 추가 메일을 보냈지만 답변을 받지 못했다. 결국 수집한 데이터를 활용한 상태로는 스토어 배포를 진행하기 어렵다고 판단했다.

프로젝트를 중단하는 대신 앱 자체는 끝까지 완성하고, 공개 가능한 부분과 그렇지 않은 부분을 분리했다.

- **코드:** GitHub 공개
- **수집한 향수 데이터:** 비공개로 분리
- **공개 데모:** 직접 제작한 가상 브랜드 20개와 향수 300개를 활용

이 문제를 겪으면서 데이터를 수집할 수 있다는 것과 실제 서비스에서 사용할 수 있다는 것은 별개의 문제라는 점을 확실히 알게 됐다.

## 4. 다음 프로젝트에서 개선하고 싶은 점

다음 프로젝트에서는 개발에 들어가기 전에 데이터 출처와 사용 가능 여부부터 확인하려고 한다.

특히 다음 항목을 먼저 검토할 생각이다.

- 이용약관에서 데이터 사용 범위 확인
- 공식 API 제공 여부 확인
- 공개 데이터인지 별도 허가가 필요한 데이터인지 확인
- 필요한 경우 개발 시작 전에 사용 허가 요청

또한 가능하면 국내 사이트나 연락이 원활한 데이터 제공처를 우선적으로 알아볼 생각이다.

이번에는 해외 사이트에 허가를 요청했지만 답변을 받지 못해 데이터 사용 여부를 확정하기 어려웠다. 다음에는 데이터의 양이나 수집 편의성뿐만 아니라 실제로 연락이 가능하고 사용 허가를 받을 수 있는지도 함께 고려하려고 한다.

## 마무리

이번 프로젝트는 단순히 앱 하나를 완성한 경험을 넘어, AI를 활용해 개발할 때 무엇을 고민해야 하는지 알게 된 경험이었다.

AI를 활용하면 구현 속도를 높일 수 있지만, 작업 방향을 정하고 결과를 검토하며 문제가 생겼을 때 판단하는 역할은 여전히 사람에게 필요했다.

아직 개발 경험이 많지 않아 부족한 부분도 있지만, 이번 프로젝트에서 겪은 문제와 해결 과정을 기록하고 다음 프로젝트에서는 같은 실수를 반복하지 않도록 계속 개선해 나가려고 한다.
